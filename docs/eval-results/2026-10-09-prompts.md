# The generator's prompts: 2026-10-09

The experiment behind the writers' prompts, and the scores of lattice's first builds of its two golden
repositories.

## Question

lattice's generator started in crystal, whose writers were told how Code Wiki writes (concrete, every name
linked, how the parts work together) and shown an example. deepwiki-by-cc's prompts add the research steps of
a writer that explores from its seed files and verifies what it says, an opening element by the kind of part
(a numbered pipeline, a field table, Parameter | Default | Effect), inline citations of the lines behind
non-obvious claims, a Sources line, and rules for diagrams. Do the additions make better pages, and what do
they cost?

## Setup

- **Repository:** crystal at `11b2542` (185,255 lines of source in 201 files), the first golden repository.
- **Build:** `lattice build` with Sonnet (`claude-sonnet-5-5`), 4 writers at once, the prompts as merged
  (crystal's and deepwiki-by-cc's).
- **Variant:** crystal's first subsection prompt, otherwise the same binary. To hold everything else still, the
  variant rewrote 16 of the build's 51 subsections, picked evenly across the outline, from a stopped build of
  the same outline, the same seed files, the same checks and the same section summaries and overview: two
  wikis that differ in those 16 subsections only.
- **Judge:** Sonnet; 20 golden questions (12 floor, 8 depth) answered from the whole wiki; pairwise on the 16
  subsections, each judged twice with the order swapped, a split counting as a tie.
- Raw scores, answers and verdicts were in `evals/results/` (not kept in git).

## Results

| | Merged prompts | crystal's first prompt |
| --- | --- | --- |
| Pairwise wins (16 subsections) | **16** | 0 (no ties, no splits) |
| Questions (the whole wiki) | 98% (floor 100%, depth 94%) | 100% (floor 100%, depth 100%) |
| Words a subsection | 1,108 | 823 |
| Links into the code a subsection | 94 | 67 |
| Citations a subsection | 17.6 | 0 |
| A Sources line | 16 of 16 | 0 of 16 |
| Opening with a numbered list or a table | 7 of 16 | 4 of 16 |
| Cost a subsection | $0.285 | $0.222 |
| Time a subsection | 51 s | 40 s |

The questions don't tell the two apart: they saturate at the top, and the one partial answer, on how memory
search ranks its entries, comes from a subsection the two wikis share word for word, so it's the judge's noise
(a first scoring had a different one partial, on the event bus, also shared). Pairwise does: the judge
preferred the merged prompts' page every time, in both orders, for its runtime detail (the exact errors, the
order keys are handled in, the fallbacks and their conditions, limits like `SGR_LONGEST`) and its organisation.
The merged pages are a third longer, which a judge can favour though it was told length alone mustn't decide.

docket's 53 dropped links were nearly all into one file, `crates/docket-tui/src/event_loop.rs`, 1.5 MB of
hand-written Rust that the scanner then took for too big to read (its cap was 1 MiB), so it had no lines for a
link to land on; the cap is 8 MiB now. The questions were answered from each wiki in parts, whole sections each
(see [evals.md](../evals.md)); a first scoring of crystal with its wiki cut at 400,000 characters gave 78%.

A sync of crystal after one commit raising a constant in `src/messages.rs` wrote again the one subsection
covering it, which now says 30, and kept the other 50, the summaries and the overview as they were: $0.17, 34 s.

Ten of crystal's subsections were checked against the code by hand, about sixty claims (defaults, limits,
timeouts, orders, error messages, file modes): every one held. What was wrong was two links the linker made, a
variant's name (`Program`) taken for a struct of the same name and a one-letter code span linked, and a writer
remarking that the outline described its part wrongly. The linker no longer links a one-letter span, a field
name several types share stays unlinked, and the writers are told never to mention the outline.

## With the symbol index

Once lattice's symbol index landed, crystal was built again at the same commit, linking through it in place of
the light scan the builds above used. rust-analyzer wasn't installed, so Rust went by its tree-sitter grammar.

The three wrong of the 50 checked by hand are the index choosing among things of one name: a struct for an enum
variant (`Stopped`, meant as a branch operation's outcome), a method for the field it reads (`selected`), and a
module for a config key (`theme`). The check also found 33 links to line 0: the index places a module that's a
whole file at no line, and the linker wrote it into the link. They now link the whole file, and the build's own
last pass, run again, put all 33 right for nothing. The questions' two partials are the event bus again, and the
memory server, where the page says a search asks the daemon and the key that it reads the database itself: the
code does both, the daemon first.

## Conclusion

The merged prompts are kept: 16 to 0 on pairwise, with the behavioural detail and the cited lines the judge
named, for about a quarter more spend a subsection. One run each, so the margin, not its size, is the result;
the questions are too easy at the top to separate prompt variants, and a harder set (more depth questions) is
the next thing the eval needs.
